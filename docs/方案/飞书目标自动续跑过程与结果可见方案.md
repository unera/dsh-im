# 飞书目标自动续跑过程与结果可见方案

日期：2026-10-31。实施基线：`main` 的 `4f1e425`，包版本 `5.8.0`。分支：`fix/feishu-goal-round-progress`。

会话开启 Goal 后，DSH 的 goal driver 会不间断注入下一轮。目标轮不是由 IM 消息发起的，飞书侧因此整轮静默：既没有过程卡，也没有每轮的结果，只有在话题里再发一条消息才能重新看到卡片。本方案让绑定到会话的飞书对话在目标轮里同样渲染过程与结果，复用 IM 轮次的现有分步直推卡片。

## 已确认的问题

一次真实会话（`session-4a08fdd4-…`）的账本里，`turn/start` 13:31、14:02 都由飞书消息发起，分别对应一张「已完成」的过程卡。15:09:51 飞书消息创建 Goal（`maxGoalRounds: 256`），15:31:13 该轮完成，下一轮的 `user/message` 由 goal driver 注入：

```json
{ "type": "user/message",
  "data": { "turn": 4, "content": [{ "type": "text", "text": "<goal_round>\nObjective: …\nRound: 1/256" }],
            "source": { "kind": "goal", "goalId": "goal-c28099e7-…", "revision": 1, "round": 1 } } }
```

此后 40 多分钟里 `tool/call`、`assistant/message` 持续产生，飞书话题却停在 15:31 那张卡片上，没有任何更新。Web 端同一时刻显示「继续执行目标」，说明差异只出现在 IM 侧。

根因是过程卡的生命周期挂在 IM 提问上，而不是挂在会话上：

- `#answerWithStepPush()`（`src/channels/feishu/bridge.mjs:5690`）是本轮唯一会 `#ensureStepCard()`/`#finishStepCard()` 的入口，只有 `#accept()` 收到入站消息时才会走到。
- `#onHarnessEvent()`（`:4623`）在 `turn/end` 之外只做会话同步镜像（`#feedSessionSyncTurn()`）。镜像要求 `sessionSyncTargetsFor(sessionId)` 返回私聊目标，而 `README.md:254` 与 `docs/PROACTIVE_DELIVERY.md:92` 都写明同步只覆盖私聊文字，群聊、Topic、Thread 不支持；本案对话正是话题，目标为空，事件被直接丢弃。
- 结果就是：目标轮的卡片从未创建，`turn/end` 也没有任何完成投递（`#deliverCompletion()` 仅服务 `/watch` 订阅）。

## 最小改动

| 位置 | 修改内容 | 复用的机制 |
| --- | --- | --- |
| `src/channels/feishu/bridge.mjs` `#accept()` | 收到入站消息、解析出 key 后调用 `rememberConversationRoute(key, { chatId, replyToMessageId })`。 | 已有 `#rememberTopicReply()` 的同一位置，key/chatId 已就绪。 |
| 同文件新公有方法 | `rememberConversationRoute()` 以 `#conversationRoutes`（LRU 512）保存「会话 key → 回复落点」，供目标轮复用；不扩展飞书 state-store 的持久化结构。 | 只作用于 bridge 内存，重启后由下一条入站消息重建。 |
| `#onHarnessEvent()` | 取 `imOwned` 后，对「有绑定对话或已有目标轮」的会话，把事件串行投给 `#feedGoalRoundTurn()`。 | 与镜像共用 `#queueEventTask()`，同一 key 上不会交错。 |
| 新增 `#feedGoalRoundTurn()` 及其辅助方法 | 识别 `source.kind === 'goal'` 的 `user/message` 开卡，`tool/call`、`assistant/message`、`turn/end` 依次喂给现有 `#appendStepCardUpdate()`/`#streamStepCardAnswer()`/`#finishStepCard()`。 | 整套分步直推卡片原语，不新增卡片类型。 |
| `#feedSessionSyncTurn()` | 同步镜像遇到 `source.kind === 'goal'` 时渲染「目标自动续跑（第 N 轮）」，不再把 `<goal_round>` 驱动提示原文贴进聊天。 | 现有 `textFromHarnessContent()` 分支。 |
| `i18n-en/feishu.mjs`、`i18n-ru/feishu.mjs` | 新增「🔄 目标自动续跑」与带轮次占位符的文案。 | 现有 `t()` 与 i18n 覆盖测试。 |

改动全部落在飞书桥内，不改 Host 契约、不改 agent 侧事件，其他渠道的现状不变。

## 目标轮的渲染

| 事件 | 处理 |
| --- | --- |
| `user/message`，`data.source.kind === 'goal'` | 对每个绑定该会话的 key 开卡，首块为「🔄 目标自动续跑（第 N 轮）」，`billable: false`；轮次取 `data.source.round`，不展示 drive 提示原文。 |
| `tool/call` | 追加 `#stepCardToolBlock()`；若上一块仍是答案流，先 `#morphStepCardAnswerToNote()` 收成摘要。 |
| `assistant/message`（`surfaceOp === 'append'` 且未被打断） | 用 `AssistantTextAccumulator` 记录，并 `#streamStepCardAnswer()` 流式写入卡片。 |
| `turn/end` | `#finishStepCard()` 封卡：写入该轮最终答案，状态按 `reason.kind` 映射为「已完成」/「已停止」。 |

卡片以回复入站消息的方式落在原话题内（`#sendCard(..., { replyTo })`），复用现有 `reply_in_thread` 与话题锚点逻辑。

## 去重与交接

- 会话同步已覆盖的会话（同一 bot 存在带 `openId` 的同步目标）由镜像负责，`#sessionSyncOwns()` 命中时目标轮不再开第二张卡。
- 目标轮与 IM 轮共用 `#stepCards` 的「每 key 一张卡」。用户中途发消息时 `#isImTurn()` 为真，目标轮直接把记录交还给本轮 ask：不封卡（封卡会截断用户正等待的回复），已流式写入的内容留在卡上，由新的 IM 轮继续封卡。
- 同一事件按 `event.seq <= round.lastSeq` 去重；同一轮重复出现 `user/message` 时由 `#goalRoundsFor()` 判断已开卡。
- 上一轮遗留的未封卡片（异常退出）在新一轮开卡前用 `#finishStepCard()` 收尾，避免两轮内容叠在一张卡上。

## 已知边界

- 会话路由只存在 bridge 内存：Host 重启后，目标轮要等下一条入站消息重建路由才会继续渲染；重启期间正在跑的轮次不会补卡。
- 目标结束（`goal/change` 完成）本身不发通知；每轮的 `turn/end` 仍有卡片收尾。若需要「目标全部完成」提示，应另做一条投递。
- `#conversationRoutes` 是跨渠道议题的通用形态，微信、企业微信等渠道可复用同一思路，本次只落飞书。
- 与 [#362](https://github.com/xmanrui/dsh-im/issues/362) 同族但不是同一处：该 issue 是目标轮里的 `ask_user_question` 投不出去，本方案修的是过程卡与结果完全不推送；两者的共同前提「非 IM 发起的轮次也需要投递目标」相互独立，可在 PR 中互相引用。
